# IMAP safety and message decoding

The Bridge client treats a single-message UID as one positive 32-bit integer.
Ranges, lists, wildcards, zero, overflow, whitespace, and command fragments are
rejected before commands are sent. Mailbox names and login credentials cannot
contain control characters; quoted mailbox names preserve literal backslashes
and quotation marks. Tags must be ordinary IMAP keyword atoms, so a user tag
cannot set a system flag such as `\Deleted`.

Search criteria accept the forms generated by the CLI: `ALL`, `UNSEEN`, quoted
`TEXT`/`SUBJECT`/`FROM`/`TO`, `KEYWORD` with an unquoted user-keyword atom,
`HEADER` with a header name and quoted value, `UID` with one UID or a `UID:*`
sequence range, and `SINCE`/`BEFORE` dates. Control characters, malformed quoting, and protocol literals are rejected
before selecting a mailbox.

Message reads, listings, and searches fetch `BODY.PEEK[]`, preserving unread
state. A successful fetch with no response for the requested UID is classified as
missing. Unrelated unsolicited FETCH updates do not change that result.
An existing message with empty or incomplete content produces a decoding error.
Server, transport, and decoding failures remain errors rather than being
reported as absence.

Draft deletion requires the server to advertise `UIDPLUS` or `IMAP4rev2` before
any flags are changed. The client marks the requested UID with `\Deleted` and uses `UID EXPUNGE`
for that UID only. It never performs mailbox-wide `EXPUNGE`, so messages already
marked deleted by another client are not removed. Servers without either
capability receive an error before deletion starts. If the scoped expunge fails after the
flag change, the requested draft may remain marked deleted; inspect its state
before retrying.

Message decoding handles MIME transfer encoding, declared character sets
(including UTF-8, ISO-8859-1, and Windows-1252), and encoded-word subjects. An
unsupported declared character set produces a decoding error when no usable
alternative body exists, instead of returning undecoded bytes. A usable inline
body remains available when another alternative cannot be decoded. Inline
plain text is preferred, with inline HTML as the fallback. Attachment parts, multipart attachments, and parts carrying file
names do not replace the message body. Indentation, trailing spaces, and blank
lines in decoded content are preserved; MIME boundary separators are not body
content.

Regression tests use disposable in-process IMAP peers and synthetic messages.
They do not require Bridge credentials, access real mailboxes, or deliver mail.
